- Conflict-marker guard (T-018): scripts/conflict-markers.mjs (findMarkers(text) returns [{ line, text }]; checkTree(root) returns [{ file, line, text }] with paths relative to root, forward slashes, files in sorted order; report(found) returns { lines, code }: { lines: [], code: 0 } for an empty list, otherwise lines is the GUARD FAIL message followed by one path:line: text per finding in the given order, and code 1; run directly it prints GUARD FAIL [no-conflict-markers]: Resolve the merge conflict; never commit conflict markers, then one path:line: text per finding, and exits 1, silent and exit 0 when clean) and tests/conflict-markers.test.js fail when any file in the repo holds a git conflict marker line. Marker rule: a line that starts in column 1 with exactly seven `<`, seven `>` or seven `|` characters, followed by a space or the end of the line (a carriage return right before the line feed counts as the end of the line). Not a marker: anything before it on the line (so a saved diff or a `path:line: text` log line is safe), eight or more of the character, seven followed by a letter or a tab, and a bare line of seven `=` (not checked on its own; it appears in Markdown and text). Files checked: every file under the repo root at any depth, found by walking the disk with no git call, so untracked files and every file type are checked (Markdown, logs and evidence included). Not opened: anything named .git (folder or file), any folder named node_modules or secrets, any file named .env or starting with `.env.`, symbolic links and junctions (not followed), and binary files (a zero byte in the first 8000 bytes, the rule git uses). Names are compared exactly, case included. The reported text has control characters removed. A file or folder that cannot be read makes the check fail with the error instead of being skipped. The command-line output and exit code are pinned by an end-to-end unit test in tests/conflict-markers.test.js (T-039): it copies the module into a throw-away folder under the OS temp dir, runs the copy with process.execPath and no shell, and checks exit 0 with no output on a clean tree and exit 1 with exactly the message line and one path:line: text line after a marker is added. Enforced through the unit tests of every verify.sh run (any --feature) and so in CI on pull requests, and by every ./scripts/guards.sh run: scripts/guards.sh calls it with the line `node scripts/conflict-markers.mjs || FAIL=1` directly above `exit $FAIL` (line 50), added by the human after the T-018 merge, who also protected both files from agent edits (deny list in .claude/settings.json and the CI step "Block changes to the checks"; commit 3931bdf, pull request #6). So no committed file, evidence logs included, may hold a marker at a line start; tests build marker strings at run time (for example '<'.repeat(7)).
