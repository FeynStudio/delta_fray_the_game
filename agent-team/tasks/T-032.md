## Coordinator choices (technical, not human decisions)
- Row 1, promisor remote. The environment the helper gives to git always carries `GIT_NO_LAZY_FETCH` with the value `1`, set after the copy of process.env so a value from outside cannot switch it off. The variable is used, not the `--no-lazy-fetch` option: a git older than 2.45 ignores an unknown variable, but stops on an unknown option, which would turn every check into SKIP.
- Rows 1, 3 and 4, one environment builder. The filter moves into one pure function that the module exports (name is the owner's choice, for example `gitEnv(source)`; it becomes the module's fifth export): it returns a copy of `source` without the seven REPO_ENV names and without the four pathspec variables of row 4, plus `GIT_NO_LAZY_FETCH: '1'`. The helper calls it with process.env. Why an export: for GIT_INDEX_FILE, GIT_NAMESPACE and GIT_PREFIX the coordinator expects (from reading, not tested) that no value changes the answer of the module's five read-only commands, so a behaviour test cannot pin those names; a table-driven test of the pure function pins every name, and the existing GIT_DIR and GIT_WORK_TREE behaviour test keeps pinning that the helper uses the filter.
- Row 2, tests for the two hardening arguments. Two fixtures, each with the hostile setting in the fixture's own .git/config and a marker file inside the fixture's base folder:
  - fsmonitor: `core.fsmonitor` set to a marker-writing command, as in gaps.mjs case e. After `checkHandoff` and `currentBranch` on that fixture no marker exists.
  - signature: `log.showSignature=true` and `gpg.program` set to a marker-writing program, and a code commit that carries a `gpgsig` header. After `checkHandoff` no marker exists. One way to make such a commit without a key: write the text of `git cat-file commit HEAD` to a file inside the fixture with a `gpgsig` header added after the committer line (first line `gpgsig -----BEGIN PGP SIGNATURE-----`, each following line of the block starting with one space, last line ` -----END PGP SIGNATURE-----`), store it with `git hash-object -t commit -w <file>` and point the branch at the new hash with `git update-ref`. `git fast-import` is another way. The owner chooses. git starts gpg.program as a program, not through a shell, so the marker program is most likely a small executable script written into the fixture folder at run time (first line built as a string in the test, file mode 0o755); whether Git for Windows and Linux both start it is for the owner to show (coordinator has not tested it).
- Rows 1 and 2, every marker test shows its fixture is live. Before the module is called, the test runs one plain git command through the fixture's own helper (which has none of the fixes) and asserts that the marker appears; it then removes the marker, calls the module and asserts that no marker exists. Without this, a fixture that does nothing on some git version or on Linux would pass for the wrong reason. No test skips itself by git version or platform.
- Row 1 fixture. One way: a fixture repo with one code commit; `extensions.partialClone=origin`, `remote.origin.promisor=true`, `remote.origin.url` pointing inside the fixture, `remote.origin.uploadpack` set to the marker command; then the loose object file of the HEAD commit's tree (`git rev-parse HEAD^{tree}`) is deleted from the fixture's .git/objects. The expected result after the fix: no marker, and SKIP 'git history cannot be read' (an existing reason; the missing object still cannot be read). The owner may build it another way if the liveness step holds.
- Row 3, tests:
  - `--first-parent`: a fixture in which a side branch adds a code file and then removes it again, and is merged into the task branch after a Handoff commit that touches agent-team/ only; the merge commit changes no path against its first parent. With the flag, the latest code commit is the code commit on the task branch; without it the walk reports a side-branch commit (the T-029 reviewer's fixture gave the commit "side removes code"). The test asserts the exact commit. Commits made in the same second can be listed in either order by a walk without the flag; the owner makes the fixture fail the same way on every run (for example by giving the side commits later commit dates) and shows three runs of the negative control.
  - Environment names: one table-driven test (or one generated test per name, as the taskFromBranch tests are) on the exported builder: each of the seven REPO_ENV names, given alone with a value, is absent from the result; an unrelated key and `GIT_CONFIG_GLOBAL` are kept with their values; `GIT_NO_LAZY_FETCH` is `'1'` in the result when the source has no such key and when the source sets it to `'0'`; the source object is not changed. The four pathspec variables of row 4 are rows of the same table.
  - Character edges: a fixture commit whose subject holds U+001F, U+007F (DEL), U+0020 and U+00A0, each built from its character code and placed in the middle of the subject (the module trims the ends, and a trim would also remove U+00A0 there): U+001F and DEL are removed, U+0020 and U+00A0 are kept, in `subject` and in `reason`.
- Row 4, large path list: the design is to ask git a yes-or-no question instead of reading the path list. Per commit the walk runs `diff-tree --quiet -r <parent> <commit> -- <pathspec for everything at the top> <pathspec that excludes agent-team/>` (root commit: `--root <commit>` in place of the two hashes), with the pathspecs as fixed literal arguments, for example `.` and `:(exclude)agent-team/`. git prints nothing; exit status 0 means no path outside agent-team/ differs, exit status 1 means one does. Only status 1 is read as "code commit"; every other failure is thrown on unchanged, so the existing SKIP reasons keep their causes. Why this and not a larger `maxBuffer`: a larger buffer only moves the limit and reads megabytes the check does not need; with `--quiet` there is no output to limit, at any commit size, and git can stop at the first differing path. What it costs: the rule "a name that does not start with agent-team/" is now applied by git's pathspec matching instead of by the module, so the brief asks for tests that the rule for C is the same (below), and the pathspec variables GIT_LITERAL_PATHSPECS, GIT_GLOB_PATHSPECS, GIT_NOGLOB_PATHSPECS and GIT_ICASE_PATHSPECS, which change how git reads a pathspec, are removed from the helper's environment by the same builder. The `log` call keeps Node's 1 MiB limit (a subject line over 1 MiB); that case is not in row 4 and is logged in BACKLOG.
  - Same rule for C, pinned by one new test on one fixture, one commit after another, each asserted as the latest code commit: a commit that only adds a top-level file whose name starts with `agent-team` but is not in the folder (for example `agent-team.txt`); one that only touches a folder such as `agent-teams/`; one that only touches a nested `docs/agent-team/` path; one that only deletes a code file. The existing tests for the root commit, the merge commit, "passes when only agent-team commits follow the code commit" and "skips a repo whose commits touch agent-team/ only" must pass unchanged; they pin the other side.
  - Large commit: shown by the evidence script on a fixture with one commit of at least 1,420,000 bytes of path names outside agent-team/ (about 20,000 files, built with one `git fast-import` process so no working-tree files are written), and a second fixture where a commit of that size touches agent-team/ only and an earlier commit is the code commit. A unit test for it is added only if it adds 1 second or less to the test file's run time on the owner's machine; if it is left out, the Handoff says row 4's large-commit case is proven by the evidence script only.
- Row 5, PATH restore: in 'skips when git cannot be run', the `finally` deletes `process.env.PATH` when it was unset at the start and assigns the saved value otherwise, the same pattern as the restore in the GIT_DIR test. No new test: the state "PATH unset at the start" cannot be made inside the test file without breaking the fixture tests. It is shown by reading (Done-when 6).
- Not changed, on purpose: the rule for C; the conditions under which the check applies; the PASS, FAIL and SKIP line wording; the existing SKIP reasons (none added, none removed, none widened); the names of the existing tests; `taskFromBranch`, `checkHandoff`, `report` and `currentBranch` signatures; that a git error gives SKIP (T-016's design); the page size and the paged walk (row 6) and one git process per commit (row 7).
- Evidence scripts (agent-team/evidence/T-032/gaps.mjs for the before and after cases, and one for the scratch-copy controls) are comment-free one-off scripts. They build fixtures only in the OS temp dir, with an empty global configuration file inside the fixture folder and GIT_CONFIG_NOSYSTEM=1, and remove them. The scratch copy of the worktree leaves out `.git`, `node_modules`, any `.env` file and any `secrets/` folder (T-029 security review, issue 5). A marker command must still work when the temp path holds a space; if an apostrophe in the temp path is not handled, the Handoff says so.
- Plain Node only, the imports the two files have today plus what the fixtures need from `node:fs`, `node:os`, `node:path` and `node:child_process`. No dependency, no network, no shell option, no command built from text, no scanner directive, no comment.
