## Goal
While a ship is spawn-protected, its outline repeatedly fades away and comes back in quick succession, so players can see it cannot be destroyed; once it moves, it is drawn normally.

## Context
Request from the human, pasted as-is:
"add T-010 as ship outline gradually disapear but maintain in loop in quick sucsessions to simulate spawn protection animation."

- Depends on the T-006 rule (human decision 2026-11-09, A2). In normal play both ships are protected at the start of the game and every respawned ship is protected until its own next move, so with this task both ships blink at game start, and the active player's ship blinks while its gauges are showing.
- Current drawing (src/render.js drawShips, read 2026-11-09): outline only, full colour, no alpha. render.js reads state only and has no clock; src/game.js step(ms) is the only place time advances.
- Paved road: FEATURE_MAP section 8 (drawn element in src/render.js reading state only; tunables in src/config.js).

## Questions for the human (answered 2026-11-09, see Decisions)
1. Blink speed: one fade cycle lasts 400 ms.
2. Fade depth: fades to fully invisible (opacity 0).
3. Loop shape: fades out, then snaps back to full opacity and repeats.

## Coordinator choices (technical, not human decisions)
- Clock: src/game.js step(ms) adds ms to a state clock field (name chosen by the owner, added to FEATURE_MAP section 9 State). The blink is computed from that clock, so __game.step drives it in tests and render.js stays read-only.
- A pure `protectionAlpha(clockMs)` in src/render.js returns the opacity (0..1) for a protected ship; drawShips uses it only for ships where isSpawnProtected(state, i) is true, and restores full opacity for everything else.
- Cycle length and minimum opacity are config values (names chosen by the owner) set from the human's answers: 400 and 0.
- Coordinator's choice for "fade out then snap back": the fade is linear in time, from 1 at the start of each cycle down toward the minimum at the end, then back to 1 at the start of the next cycle: alpha = 1 - (1 - min) * ((clock mod period) / period). With min 0 this gives 1, 0.75, 0.5, 0.25 at 0, 100, 200, 300 ms and 1 again at 400 ms. The human can ask for a different curve on localhost.

- Design verdict: CHANGES NEEDED

No exploit: a protected ship can't be destroyed and is never a danger to the mover, so its invisible moments hide nothing that matters.

Why it matters to the player: flicker comfort and readability. Asked for: a short real-frame-rate recording of game start or a respawn, or a human localhost check recorded in the brief before approval.
- Suggested ideas:
  - Start each ship's blink when it respawns, not on the shared game clock. Right now a respawned ship can appear at about 0 opacity on its first frames, so it pops in invisible. This is a timing detail, not a change to the human's curve.
  - A first-time hint (a short line or a legend) explaining that a blinking ship can't be destroyed until it moves. Today nothing on screen teaches the A2 rule.
  - Optional reduced-motion or accessibility setting that swaps the blink for a steady faint outline when `prefers-reduced-motion` is set.

  - Does the hard snap back feel like a retro invulnerability blink, or like a glitch or a strobe? Is 400 ms comfortable over a long session?

Also: protection and the blink both ignore time, so a ship that is never moved blinks for as long as it isn't moved. That follows the A2 rule (time limits are out of scope) and is worth watching in playtests.
