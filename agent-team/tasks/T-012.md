## Goal
Each player sees their own score in a corner of the screen: it goes up by 1 for every enemy ship they destroy and down by 2 each time their ship dies by hitting the wall.

## Context
Request from the human, pasted as-is:
"add T-012 as adding a score count for each ship in the corner to keep track of amount of enemy ships destroyed. destroying 1 enemy ship plus 1 score. hitting wall and die minus 2 points."

- docs/PLAN.md: endless play, no end condition; nothing about score. Not in DESIGN.md "Do NOT Add". T-007 listed "score or kill counters" as out of scope there.
- Current rules (src/rules.js resolveMove, read 2026-11-09): an enemy swept by the mover gets alive: false; the mover gets alive: false if its swept area touches a wall; hit-then-wall destroys both. State is { turn, ships, gauge } (FEATURE_MAP section 9); scenario picks are field-specific, so a new state field does not change expected/.
- Paved road: FEATURE_MAP section 8 (new game rule = pure function in src/rules.js plus tests; new drawn element = draw<Thing>(ctx, state) in src/render.js).

## Questions for the human (answered 2026-11-09, see Decisions)
1. Starting score: 0 for both players.
2. Scores can go below 0 (a wall death at 0 gives -2).
3. Corners: player 1 top-left, player 2 top-right, each in its ship colour.
4. Hit-then-wall in one move: both apply (+1 and -2, net -1).

## Coordinator choices (technical, not human decisions)
- State gets `scores: [p1, p2]` (added to FEATURE_MAP section 9 State); createInitialState sets the start value from config. A state without `scores` (all scenario states, older test states) is treated as starting from the config value, so existing scenarios and expected/ files are unaffected.
- A pure `scoreMove(before, after)` in src/rules.js returns new scores from the state before resolveMove and the state after it: +config.scoreKill for each enemy that went from alive to destroyed, config.scoreWall (negative) if the mover was destroyed. game.js computes it when it launches the move (where it calls resolveMove) and puts the new scores into state in the step where the move animation ends, together with endTurn and the respawn, so the score never changes before the player sees the hit. Points live in config so the human can tune them.
- Only the mover can score in a move, because only the mover sweeps and only the mover can hit the wall.

### Design Review round 1 (2026-11-10)
- Design verdict: CHANGES NEEDED
- Issues:
  1. Corner score, negative values: no screenshot shows a negative score (for example "-2" or "-4") on screen. Only the fake-canvas test checks the minus sign. If the minus is drawn wrongly or cut off at the corner, a player cannot tell they are below zero. Fix with evidence only: add a screenshot taken after a wall death, or with scores set through the debug API to something like [-2, -4]. Also check that the right-aligned player 2 score stays inside the border.
  2. Score change timing, on screen: no frame shows when the score changes compared with the hit. Tests pass, but nothing visual was captured. If the number changed before the hit was visible, players would be confused. Fix with evidence only: two screenshots or a short recording, one in the last frame before a kill or wall-death move ends (score unchanged) and one in the next frame (score changed, explosion started).
  3. Corner score, first-time player (minor, not blocking alone): the score is a bare number with no label, and it changes with no "+1" or "-2" cue. A first-time player who loses 2 points at the wall may not know why. Colour and side show whose score it is, but not what earns or loses points.
- Suggested ideas:
  - A short floating "+1" or "-2" in the player's colour near the corner score (or at the explosion) when it changes.
  - A small label such as "P1" or "SCORE" next to each number, or a one-line rule note on first load.
  - When a ship moves under its corner score, draw the score over the ship or fade the score.
- Playtest questions:
  - Without being told, do new players work out what the corner numbers mean and why they went down by 2?
  - Does the score changing as the explosion starts feel connected to the hit, or does it get missed?
  - Is 28-unit text easy to read on a laptop screen or in a small browser window?
  - Does -2 for a wall death make players too cautious near the edges, given the edge-death rate is already about 0.1%?
  - Later, when paid moves arrive: does a visible running score make "who paid more" feel like "who is winning"?
- REPEATS: none known; this is round 1.
- Promote to guard: a smoke check that screenshots a state with a negative score and checks the minus sign is drawn and the text stays inside the map border at 1920x1080 and 1000x1000. This would replace the fake-canvas-only check.
- Risk for the human:
  - The score is the first visible measure of "who is ahead". Under pay-to-play, more paid moves means more chances to kill, so the score could start to read as a pay-to-win scoreboard. The score's rules are fine; this belongs under DESIGN.md's open question on who wins.
  - The scores are placed with the left-or-right alternation in `drawScores`, so a third player (the three-factions pillar) would land in the top-left corner on top of player 1. That needs a decision before a third player is added.
