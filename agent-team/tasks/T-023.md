- What counts as a comment:
  - .js/.mjs: `//` to the end of the line and `/* ... */`, found by a tokenizer that knows single- and double-quoted strings, template literals (text parts are not code; code inside `${ }` is code again, nested to any depth), regular expression literals (including `/` inside a character class) and division. Line 1 starting with `#!` is a shebang, not a comment.
  - .sh: `#` at the start of a line or right after whitespace, outside single and double quotes. So `$#`, `${#files[@]}` and `#` inside quotes are not comments. Line 1 starting with `#!` is a shebang. Here-documents are not handled; none exists today. If one is ever needed, that is a new brief.
  - .html: `<!--` anywhere; `/*` inside a <style> block; the body of an inline <script> block is checked with the .js rules. `<!doctype html>` is not a comment.
- Allowlist (coordinator's reading of "the two `// nosemgrep` lines"): exactly two entries, each a file plus the full comment text, with no line number, so the entries survive line moves:
  - scripts/run-scenario.mjs: `// nosemgrep: javascript.lang.security.insecure-object-assign.insecure-object-assign`
  - scripts/smoke.mjs: `// nosemgrep: javascript.lang.security.detect-insecure-websocket.detect-insecure-websocket`
  - Any other comment is a finding, including a nosemgrep directive in another file, a different rule id, or extra text after the directive. A new scanner directive therefore needs a brief that changes the allowlist. This is stricter than allowing every `// nosemgrep:` comment, which would let any agent silence the scanner without anyone noticing.
- The two new files hold no comment themselves, and no text that a plain grep would take for one: test fixtures are built as strings at run time (for example '/'.repeat(2) + ' note', '/' + '*', '<' + '!--'), and the allowlist texts are stored without their leading slashes and compared after adding them at run time.

- What the tokenizer does not handle:
  - .js/.mjs: it is not a parser. A slash is read as division after a closing round, square or curly bracket, after ++ or --, and after a name or a number. It is read as the start of a regular expression after any other punctuation and after return, typeof, instanceof, in, of, new, delete, void, throw, case, do, else, yield, await. So a regular expression right after a closing round or curly bracket (for example an if condition followed directly by a regular expression) is read as division, and a division right after a property called in or of is read as a regular expression. On such a line a comment can be missed or text can be flagged wrongly. No such line exists in the tree today. Also not handled: JSX; a byte-order mark before a line-1 shebang (the shebang would be reported); a string or regular expression left open is ended at the line end.
