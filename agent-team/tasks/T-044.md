## Goal
The flash-rate test stays green for every blink the rule allows, including a shallow one that never fades below 0.5, so a valid config change cannot fail it.

## Context
BACKLOG line, as logged (from T-019 night shift 2026-11-20; phase 1):
"Make the T-019 snap-back test in tests/flash-rate.test.js pass for a valid shallow blink (config.protectionMinAlpha 0.5 or higher), which it would fail today (from T-019 night shift 2026-11-20; phase 1)."

Source: agent-team/tasks/T-019.md, Review round 1, Issue 4: "the snap-back test counts rises greater than 0.5. If protectionMinAlpha is later set to 0.5 or higher (a shallow blink that the rule exempts), the snap-back test fails on a valid config."

Files read by the coordinator on master (2026-11-21):
- tests/flash-rate.test.js: countSnapBacks(periods) counts steps where `alpha - previous > 0.5` (fixed threshold); the last test asserts 10 ±1 snap backs over 10 periods at the current config. withConfig(overrides, fn) restores protectionBlinkMs and protectionMinAlpha in a finally block.
- FEATURE_MAP section 2: render.protectionAlpha falls linearly from 1 to config.protectionMinAlpha over each config.protectionBlinkMs, then snaps back to 1. A snap back is therefore a rise of (1 - protectionMinAlpha), which is 0.5 or less once protectionMinAlpha is 0.5 or higher.

Coordinator recommendation (technical, the owner may choose another way that meets Done when): count a rise as a snap back when it is larger than half of (1 - config.protectionMinAlpha), read at call time. A protectionMinAlpha of exactly 1 means no blink; the test asserts 0 snap backs in that case.
