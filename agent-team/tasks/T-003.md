# T-003 Movement: the second Space flies the ship the locked distance and direction (Prototype 1, slice 3)
Status: READY
Owner role: Owner
Created: 2026-11-08
Verify feature: movement  (passed as --feature to every verify.sh run for this task)

## Goal
After the second Space, the active ship flies in a straight line, over a short animation, the distance locked on the power gauge in the direction locked on the direction gauge (forward or backward), ends where rules.applyMove says, and the gauges come back for the next move.

## Context
Request from the human, pasted as-is:
"build movement: second space moves the ship the locked distance and direction"

- This is slice 3 of the build order in docs/DESIGN.md ("movement"). Starting point: product-a master at 0858c9c (T-002 merged).
- Feature map: agent-team/FEATURE_MAP.md section 4 (Movement), section 1 (debug API), section 8 (paved roads), section 9 (harness contract: Move shape, applyMove, gauge, debug API `step(ms)`).
- Spec for the check: scenarios/movement.json and expected/movement.json, run by scripts/run-scenario.mjs (inputs deep-frozen, numbers rounded to 3 decimals). Do not edit them. Note the scenario states have no `gauge` field, so applyMove must not need one.
- Design: docs/DESIGN.md and docs/PLAN.md "Controls" (forward moves turn the ship to face its travel direction; backward moves keep its heading).
- What T-001 and T-002 built (read these first):
  - src/rules.js: only `createInitialState()`.
  - src/input.js: pure `stepGauge`, `pressKey`, `keyFromEvent`. The second Space sets `gauge.phase = 'moving'` and keeps `needle`, `backward`, `distance`. Convention (comment at the top of input.js and FEATURE_MAP section 3): world travel angle = heading + needle when forward, heading + 180 + needle when backward; positive = clockwise, like heading.
  - src/game.js: owns `state`; `press(key)` and real keydown go through `pressKey`; `step(ms)` only calls `stepGauge`, which does nothing in the moving phase; the rAF loop calls `step(elapsed)`; ?debug=1 exposes getState/setState/press/step.
  - src/render.js: `drawGauge` draws nothing in the moving phase.
- `--feature movement` runs guards, lint, unit tests and the movement scenario. It has no browser step, so the agent can run it. There is no movement browser smoke check, so the game.js wiring and the animation are checked by unit tests (below), including one that loads the real src/game.js in Node with a stubbed DOM (the reviewers of T-001 and T-002 already probed game.js this way).
- After the move, in this slice: the gauge goes back to the power phase and the same player keeps the turn. Passing the turn, respawn and `endTurn` belong to the turns slice (FEATURE_MAP section 6), and hits and walls to the hits slice (section 5); until then a ship can fly past the map edge. This is a slice boundary taken from the DESIGN.md build order, not a game rule.
- Stack and scope: plain JavaScript (human decision of 2026-11-07). Slim outline-only ships (2026-11-08).

- [ ] applyMove refuses a move longer than the max (human decision of 2026-11-08, see Decisions): when `move.distance > config.maxMove` it returns the state unchanged, so the ship stays where it is with the same heading; a move of exactly `config.maxMove` is still made. tests/movement.test.js checks this with deep-frozen input at the default maxMove (for example distance maxMove + 1 leaves the state deep-equal to the input, and distance maxMove moves the full distance) and with `config.maxMove` overridden (for example to 200: a 200-unit move is made, a 201-unit move is refused). No change to scenarios/ or expected/.
- [ ] src/input.js exports a pure function that turns a locked gauge into a Move `{ distance, angle, backward }` using the ship whose turn it is and the T-002 convention (angle = heading + needle forward, heading + 180 + needle backward, kept within 0 to 360). tests/input.test.js checks forward and backward at several headings and needles, including the FEATURE_MAP section 3 example (60% power, needle 30, forward, heading 0 gives distance 0.6 x maxMove at angle 30).
- [ ] src/game.js, on the second Space (real key or `press('Space')`), builds the Move from the gauge, gets the end state from `rules.applyMove`, and animates the ship there; `step(ms)` advances the animation and, once the animation time has passed, sets the ship to exactly the applyMove result and puts the gauge back in the power phase with the same `turn`. The animation length is in src/config.js. tests/game.test.js loads the real src/game.js in Node with a minimal stubbed DOM and `?debug=1`, and checks through `window.__game`:
  - from the spawn state, power 0.6 locked, needle 30 forward, second Space, then `step` past the animation: ship 0 ends at the applyMove result for `{ distance: 0.6 x maxMove, angle: 30 }` (within 0.001) with heading 30; ship 1 is unchanged; `turn` is still 0; gauge phase is 'power';
  - the same with Shift (backward): the ship moves toward its tail side and its heading is unchanged;
  - halfway through the animation the phase is still 'moving', Space and Shift change nothing, and the ship is not yet at its end point;
  - a large `step(ms)` never takes the ship past the applyMove end point.
- [ ] While the ship moves, the drawn ship is on the straight segment between its start and the applyMove end point, never beyond it, and the final position comes from applyMove, not from the animation. No path line, trail or end-point marker is drawn (DESIGN.md "Do NOT Add"); the reviewer reads the draw code to confirm.

## Decisions
(human answers only, one line each, also copied to agent-team/DECISIONS.md)
- Decided by human in session, 2026-11-08: "refuse the move and leave ship where it is."
  Context: answers the coordinator's question about a move longer than maxMove (refuse vs. shorten to maxMove).

Coordinator recommendation (owner may choose differently if it passes the Done-when checks; state the choice in the handoff):
- Animation: a fixed time per move, about 600 ms, in config (for example `moveAnimMs`), with constant speed along the segment. A forward move turns the ship to its new heading when the move starts.
- Keep the animation's progress in the state object game.js owns (an extra field is fine; getState/setState copy it), so `step(ms)` and the tests can drive it.
- In the handoff, list as "Not verified" anything only a real browser shows (smoothness, the look of the move), unless the human checks it on localhost.
