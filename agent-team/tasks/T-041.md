## Coordinator choices (technical, not human decisions)
- Files:
  - scripts/home-paths.mjs (new). Exports:
    - `findHomePaths(text)` returning `[{ line, kind }]`, one entry per line that holds a hit, kind `windows`, `drive-mount` or `home` for the first hit on that line;
    - `checkTree(root)` returning `[{ file, line, kind }]` for every file under `root` that the skip list does not skip, paths relative to root with forward slashes, files in sorted order; it throws when `root` is missing or a file or folder cannot be read;
    - `report(found)` returning `{ lines, code }`: `{ lines: [], code: 0 }` when empty; otherwise the line `GUARD FAIL [no-home-paths]: Replace the home-directory path with a placeholder such as <OS temp dir> or <user>; never commit an account name` followed by one `path:line: <kind> home-directory path` per finding, and code 1.
    Run directly (`node scripts/home-paths.mjs`) it checks the repo it lives in (the folder above scripts/), writes the report lines and exits with the report's code; importing it does not run this part (the isMain pattern).
  - tests/home-paths.test.js (new): the checker's own tests, a test of the command-line run (Done-when 6), and one tree test on the real repo that fails, listing every `path:line: kind`, when anything is found.
- Never echo the match: no return value, report line or test message holds the matched text or any part of the line, only path, line number and kind. So a failing run's log, saved as evidence, does not itself hold the path it reports.
- Scope (confirmed, answers 1 and 5): every file under the repo root at any depth, found by walking the disk with no git call, so tracked, untracked and ignored files are checked alike; every file type. The scope is the root the caller passes; there is no list of folders to check.
- Skip list (coordinator choice; nothing else is skipped, and each item has a test in Done-when 4):
  - Anything named `.git` (the folder in the main checkout, the file in a worktree): git's own data, not repo content. Object files are compressed, so a text pattern cannot be found in them anyway; a path in an old commit is not removed by any check of the tree (see Not covered); and git's own files may hold machine-local paths by design.
  - Folders named `node_modules`: installed by npm ci (in CI too, inside the checkout), not written by the team, not committed; third-party text there can hold such paths and nobody here can fix it.
  - Folders named `secrets`, files named `.env` and files starting with `.env.`, except `.env.example`: as in scripts/conflict-markers.mjs, no checker in this repo opens a file that may hold a secret. `.env.example` is the committed template AGENTS.md names ("cp .env.example .env") and holds no secret, so it is checked (none exists today). This is the one place where this checker differs from the T-018 walk.
  - Files with a zero byte in their first 8000 bytes: binary files such as the PNG screenshots in evidence, where a text pattern means nothing; same rule as scripts/conflict-markers.mjs. UTF-16 text is skipped by the same rule (see Not covered).
  - Links (to folders or files) are not followed: a link can point outside the repo, into a home folder for example, and following it would check files that are not the repo's and could loop.
- False hits (coordinator choice): no allowlist and no exemption by file, folder or path. Files that legitimately talk about these paths stay clean by how they are written, not by being skipped:
  - scripts/home-paths.mjs: its patterns are code. They are written so that the source text is not a hit: right after each separator in a pattern comes a character class, a group or an escape, never a name character (a `[`, `(` or `\` after the separator). No pattern is built from a variable.
  - tests/home-paths.test.js: every fixture is joined at run time from pieces (see below), so the source never holds a joined path.
  - This brief, the other briefs, agent-team/BACKLOG.md, DECISIONS.md, REPEATS.md, FEATURE_MAP.md and the review records: such paths are written only with a placeholder right after the separator (`<user>`, `<name>`, `<account>`, `<drive>`, `%USERNAME%`, `$USER`), as they already are; the placeholder rule passes them.
  - Evidence: a command that spells a pattern writes it as a regular expression (a `[` or `(` right after the separator); search outputs keep `file:line` only; the T-030 placeholder `<OS temp dir>` stays as it is.
  - Logs that verify.sh writes into the checkout during a run, in CI too: checked like any file (Done-when 10).
  - Proof: the real-repo tree test walks all of these with no exemption (Done-when 7), Done-when 8 shows a joined path in any of them is caught, and the checkTree tests pin that the checker's own two file names are not skipped (Done-when 4).
  - Why no allowlist: a listed file is a place where a real path can hide, which is the T-030 failure this check exists for; and today no file needs one. If a file ever has to hold a real-looking path on purpose, that is a new brief and the human's choice.
- Patterns (confirmed, answer 2), written here without a real name; a "name character" is a letter, a digit or `_`:
  - windows: a drive letter, `:`, one or more `\` or `/`, the word Users in any letter case, one or more `\` or `/`, then a name character. This covers the backslash form, the forward-slash form, the form with doubled backslashes inside JSON text, a `file:///` address, and short 8.3 names.
  - drive-mount: `/`, one letter, `/`, Users in any letter case, `/`, then a name character (Git Bash `/<drive>/Users/<name>` and WSL `/mnt/<drive>/Users/<name>`).
  - home: `/Users/` (macOS, exact case) or `/home/` (Linux) followed by a name character, where the `/` before Users or home is at the start of the line or follows a character that is not a name character, `.` or `-` (so a web address such as `example.com/home/page` is not a hit).
- Not a hit (placeholder rule, confirmed, answer 3): anything where the character after the separator is not a name character, for example `<user>`, `<account>`, `%USERNAME%`, `$USER`, `${USER}`, `~`, `*`, a backtick or the end of the line; Users or home without a drive letter or leading separator as above; a folder name such as `/homework/`. So the placeholder text already in the repo stays as it is. No exceptions by name: a public or CI account folder (for example the runner account's home folder on a CI machine) is a hit like any other (fix: a placeholder).
- Not covered, said in the Handoff and the FEATURE_MAP line: a bare account name with no path (answer 4); the backslash form with no drive letter and UNC paths; a lower-case macOS form with no drive letter; macOS per-user temp folders under /var/folders (they hold no name); paths split over two lines, URL-encoded or written with escapes other than doubled backslashes; UTF-16 text and other binary files; file and folder names (only content is read); the skipped places; git history (commits already made, for example T-030's three branch commits that never reached master).
- In a failing run Node's error output can hold absolute paths. In a checkout under a home folder (CI, or a scratch copy in the OS temp dir on Windows) such a log is a true hit: it fails the next runs until the path is replaced by a placeholder or the log is removed. The FEATURE_MAP line says so.
- Test fixtures are built at run time from pieces (for example a drive letter, the separator and a fake name joined in code), so no source file, saved output or evidence file ever holds a joined path. The fake name is a plain word such as `someone`; it is never a real account name.
- Plain Node only: node:fs, node:path, node:url, node:os (temp dir), node:child_process (in the test only, Done-when 6), node:test, node:assert. No dependency, no network, no eval, no regular expression built from a variable, no Object.assign, no scanner directive, no comment, no console or util.format call.
- Time: the walk is the same size as the real-repo tree test of tests/conflict-markers.test.js, which already runs in every verify.sh run.
