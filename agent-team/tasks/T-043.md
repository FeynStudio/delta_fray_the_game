## Coordinator choices (technical, not human decisions)
- Which process to end. Because the launcher can hand off to a detached browser (FEATURE_MAP, commit ef1704e), `proc.pid` may not be the process that holds the profile. After `await cdp.ready`, launchBrowser asks the browser once for its own process id with the browser-level DevTools message `SystemInfo.getProcessInfo` (no session id) and keeps the id of the entry whose type is `browser`. If the message fails or reports no such entry, the run goes on, the id stays unknown, and stderr gets the fixed line `smoke: browser process id not reported`; the close then behaves as today. Done-when 3 first confirms on BASE that the browser reports this entry and whether it differs from the launcher's id.
- How it is ended. In the browser close method, after today's lockfile wait: if the lockfile is still there and the browser's process id is known, `process.kill(<that id>)` (TerminateProcess on Windows, SIGTERM elsewhere), then a second wait of up to 10 s for the lockfile to go, with the fixed stderr line `smoke: browser ended by its process id after it kept its profile`. No child_process call, no shell, no `taskkill` or `tasklist`, and never a kill by image name or by any id the browser did not report itself. proc.kill() stays as today. Chrome's helper processes (renderer, GPU, utility) are expected to end with their browser process; Done-when 5 counts them.
- Profile removal. The `rmSync(profile, ...)` call in the main block's finally is wrapped: if it throws, stderr gets exactly one line `smoke: browser profile folder <basename of the profile folder> not removed (<error code>)`, the exit code becomes 1, and the main block goes on to write the result file and the screenshots as today. The line holds the folder's base name (galaxy-smoke- plus the random suffix, no user name) and the error code only: no message text, no absolute path, no stack trace.
- Parts of scripts/smoke.mjs this task may change: launchBrowser from `await cdp.ready` to its return statement (the one new message and the id it keeps), the browser close method, and the main block's finally plus the declaration it needs. Everything else stays byte for byte: the imports (unless a name already imported from a node: module is added to an existing import line), findBrowser, connect, the spawn call and its flags, the port-file and address code (the scanner directive line included), open() and the page object, every probe, stateShot, phaseShot, FEATURES and its result keys, the constants, and the usage check.
- The leak itself is not reproduced on BASE (it leaves a browser and a folder, as the T-040 reviewer's probe did). The before state is shown by reading BASE and by the two T-040 review records; the fix is shown on the committed change with scratch changes.
- Leftover counts (working rule for this task): after every smoke run of this task, about 15 s after it ends, the owner counts the `galaxy-smoke-*` folders in the OS temp dir and the processes of the browser findBrowser picks by image name (chrome.exe here; msedge.exe if Edge is picked), against a baseline taken before the first run, with agent-team/evidence/T-040/count-leftovers.mjs or a comment-free copy of it under agent-team/evidence/T-043/ with the image name changed. Counts only: no process command line (listing command lines is refused by the permission system; T-030 security review Issue 4, T-040 Handoff "Not verified"), no process path, no temp-dir path. If a count is above the baseline, the Stop rule applies; agents never end a process by image name and never delete the folder themselves.
- The exit code of a run in which the browser had to be ended by its id but the profile was then removed: as the feature produced it (0 when the results are complete), because nothing is left behind; stderr says what happened. Done-when 5 shows it.
- Not tested, and why: a browser that really stops answering (a skipped Browser.close send stands in for it, as in T-040); Edge, Linux and macOS (SIGTERM on POSIX is not run); a process id reused by another process between the lockfile wait and the kill (the window is the length of one existsSync call after a 10 s wait; the Handoff lists it as a known limit); a browser that fails to start or to connect (see Out of scope).
