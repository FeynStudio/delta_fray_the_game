## Coordinator choices (technical, not human decisions)
- Why an ignore rule works: `git worktree remove` refuses only on modified tracked files and on untracked files that are not ignored, and deletes ignored files with the folder. Linked worktrees read info/exclude from the common git dir. Both come from git's documented behaviour and are not yet run; Done-when 2 (c) to (e) and 4 prove them.
- Rule shape: anchored to agent-team/evidence/ and to the `-review` suffix, so it ignores agent-team/evidence/T-049-review/ and does not ignore agent-team/evidence/T-049/ or any owner label. In git's pattern syntax `[0-9]*` is one digit then any characters other than `/`.
- The test never reads or runs git in this repo: every git call runs with its cwd inside a throw-away folder made with mkdtempSync under resolve(os.tmpdir()), and the test writes the rule into that throw-away repo's own .git/info/exclude. So it passes the same way in CI and on a fresh clone, where no exclude rule exists.
- git is called only as `execFileSync('git', [array literal], options)` or `spawnSync('git', [array literal], options)` with no shell, `env: gitEnv(process.env)`, `windowsHide: true`, and stderr not inherited (`stdio` set so git's messages, which hold temp paths, never reach the test output). The throw-away commit uses `-c user.name=t -c user.email=t@example.invalid -c commit.gpgsign=false`.
- No test name, assertion message or printed line holds an absolute path: on Windows the OS temp dir sits under the home folder, and such a path in a failing verify log trips the home-path guard (FEATURE_MAP line 95).
