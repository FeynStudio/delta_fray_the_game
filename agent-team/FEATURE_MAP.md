Feature Map - product-a (Galaxy Shooter - Prototype 1)
Feature plan doc: docs/PLAN.md source of truth for game features plan.
Roles: Coordinator, Owner, Reviewer.

1. Agent test hook (applies to all features)
The game draws on a canvas, so agents can't click elements. src/game.js exposes a debug API when the URL has ?debug=1:
- window.__game.getState(): ships, positions, headings, turn, gauge state
- window.__game.press('Space' | 'Shift'): simulates input
- window.__game.setState(state): loads a test scenario
- window.__game.step(ms): advances the game clock
Command-line checks: ./scripts/verify.sh T-### --feature <name> always runs guards, lint and all unit tests (node --test tests/*.test.js), then that feature's scenario and/or browser smoke check. --feature all (the default) runs every feature, so it only passes once the whole prototype is built. See section 9 for the harness contract.

2. Map & Rendering
- What it does: "I see the play area full screen with two triangle ships."
- Where it lives: src/render.js, src/config.js (ship triangle: rules.shipPoints, re-exported by render.js, T-004). Explosions (T-007): render.js explosionPieces(explosion, elapsedMs) (pure: the ship's outline triangle, each side cut once at config.explosionCuts, 6 pieces whose midpoints move straight out from the centre at config.explosionSpeed units/s and that shrink about their midpoints from 1 to config.explosionEndScale over config.explosionMs) and drawExplosions(ctx, state) (outline pieces in COLORS.ships[ship], config.shipLineWidth; drawFrame calls it before drawShips). Scores (T-012): drawScores(ctx, state) draws player 1's score top-left and player 2's top-right (right-aligned), each in its ship colour, config.scoreFontSize, config.scoreMargin inside the map; drawFrame calls it right after drawMap. Spawn protection blink (T-010): render.js protectionAlpha(clockMs) (pure: each cycle of config.protectionBlinkMs (600) falls linearly from 1 to config.protectionMinAlpha (0), then snaps back to 1; no fade back in; read at call time); drawShips strokes a ship with globalAlpha protectionAlpha(state.clock) when rules.isSpawnProtected(state, i) is true, else 1, and resets globalAlpha to 1 after every ship, so gauges and the other ship are unchanged. state.clock is advanced only by game.js step(ms) (section 9). Title decal (T-011): render.js drawTitle(ctx) (reads nothing from state) strokes config.titleText ("Delta Fray", the human's words) upper-cased as "DELTA FRAY", outline only in COLORS.dim, monospace config.titleFontSize, config.titleLetterSpacing, config.titleLineWidth, textAlign centre at x = config.worldWidth / 2, config.titleTop below the top edge; wrapped in ctx.save/restore so later draws keep their own settings; drawFrame calls it last, after every other draw call. Decoration only: not in state or rules.js, so movement, hits and walls are unchanged
- How a user reaches it: open index.html through a local server (e.g., npx serve .)
- How an agent drives it: ?debug=1, then __game.getState(); screenshot the canvas; verify.sh --feature render
- Inputs: world 1280 × 960 units, browser window 1920 × 1080
- Correct output looks like: world scaled to fit with aspect ratio kept; ships are 30-unit triangles at their spawn points, pointing at each other; no scrollbars; a destroyed ship's outline breaks into 6 uneven pieces that fly outward and shrink to half size over 1 second while play carries on (T-007); a spawn-protected ship's outline fades out over 600 ms, snaps back and repeats until that ship moves (T-010); "DELTA FRAY" in outline capitals at the top centre, over everything, ships visible through and under it (T-011)
- Known traps: mixing screen pixels with game units; stretching the map at other aspect ratios; blurry canvas on high-DPI screens
- Owner role: Owner

3. Controls & Gauges
- What it does: "I press Space to set distance, Shift to flip backward, Space again to launch."
- Where it lives: src/input.js (pure: stepGauge(state, ms), pressKey(state, 'Space' | 'Shift'), keyFromEvent(event)); keydown listener, animation loop and debug API in src/game.js; drawGauge / drawPowerBar / drawDirectionDial / gaugeLayout(state) in src/render.js (drawn only on the ship whose turn it is and following its position and heading every frame: power bar at 0.3 of base size a fixed distance below the ship that clears the dial in every heading, so it never moves with the phase; fixed-size direction dial at 0.56 of base size just in front of the nose, or just behind the tail when backward, on the long axis; clamped inside the map near edges); sweep speeds, needle range and gauge layout in src/config.js (gauge*) (T-002)
- Gauge state notes (T-002): the gauge also carries sweep: 1 | -1 (direction the active reading moves in), so a gauge edited through setState keeps sweeping smoothly. Both readings bounce back and forth. needle stays within -gaugeNeedleMax..+gaugeNeedleMax, positive = clockwise; backward: false measures it from the nose (world angle = heading + needle), backward: true from the tail (world angle = heading + 180 + needle). Shift toggles backward in the direction phase only. In the moving phase step(ms) runs the move animation instead (section 4); a moving phase with no anim (only reachable through the debug setState) is reset to the power phase on the next step(ms) > 0, ship unmoved, turn unchanged (T-014, human decision 2026-11-09).
- How a user reaches it: keyboard during their turn
- How an agent drives it: __game.press('Space'), __game.step(ms), __game.press('Shift'), __game.press('Space'), then check getState().gauge; verify.sh --feature input
- Inputs: Space at a 60% power reading; no Shift; Space at a 30° needle reading
- Correct output looks like: distance locked at 90 units (60% of 150), direction 30° forward, launch starts immediately with no confirm step
- Known traps: key-repeat registering multiple presses; Shift working after the direction is locked; gauges sweeping too fast for careful aim; adding a path preview (not allowed)
- Owner role: Owner

4. Movement
- What it does: "My ship flies the distance and direction I chose."
- Where it lives: src/rules.js applyMove(state, move) and wrapDegrees (math; a move longer than config.maxMove is refused and the state returned unchanged, human decision 2026-11-08; every accepted move, forward or backward, sets the heading to the wrapped travel angle, so a backward move turns the ship to face its path at launch, flies tip first and keeps that heading, human decisions 2026-11-09, T-009); src/input.js moveFromGauge(state) (locked gauge to Move), pointAlong(from, to, t), startMove(state, end) and stepMove(state, ms) (animation progress kept in state.anim = { from, to, ships, elapsed, scores? } (scores added by game.js at launch, T-012), where ships is every ship of the rules.resolveMove end state; only the mover goes along the straight segment at constant speed, and at the end all of anim.ships is put in place, so the mover ends exactly on the rules result and a destroyed enemy stays destroyed; the gauge returns to the power phase; a moving phase with no anim, only reachable through the debug setState, is reset by stepMove to the power phase on the next step(ms) > 0 with every ship unmoved, no move built and the turn unchanged, so game.js calls no endTurn: T-014, human decision 2026-11-09); src/game.js press() launches on the second Space with rules.resolveMove, and step(ms) runs stepMove and, in the step where the animation ends, calls rules.endTurn once (section 6) (T-003, T-005); drawShips in src/render.js draws the ship where state puts it (no path, trail or end marker); animation length config.moveAnimMs (T-003)
- How a user reaches it: the second Space press
- How an agent drives it: unit test calling rules.applyMove(state, {distance, angle}); tests/game.test.js loads src/game.js in Node with a stubbed DOM and drives __game.press/step; verify.sh --feature movement
- Inputs: ship at (200, 480) heading 0°, move 150 units at 0°
- Correct output looks like: ship ends at (350, 480). Every move, forward or backward, turns the heading to the travel direction and keeps it: a backward move (Shift) snaps the ship to face its path at launch, flies tip first, and on its next turn the gauges sit at the new nose (T-009).
- Known traps: degrees vs. radians; y-axis pointing down on canvas; allowing distance over 150; letting the animation, not rules.js, decide the final position
- Owner role: Owner

5. Hit Detection & Edges
- What it does: "If my path sweeps over the enemy, it explodes. If I reach the wall, I explode."
- Where it lives: src/rules.js resolveMove(state, move) (applyMove, then the convex hull of the mover's start and end triangles in its new heading (the travel angle, for backward moves too, T-009), as input.startMove turns the ship before it moves; separating axis test against each living enemy, touching counts, except an enemy for which isSpawnProtected(state, j) is true, which survives the sweep (human decision 2026-11-09, A2; T-006); the mover is destroyed if any hull corner touches or crosses 0..config.worldWidth or 0..config.worldHeight, human decision 2026-11-09; a move over maxMove returns the state unchanged) and shipPoints(ship, size, width) (the one ship triangle, also drawn by render.js); tests in tests/hits.test.js (T-004) and tests/spawn.test.js (T-006). Called by src/game.js press() for every launched move (T-005). Score (T-012): src/rules.js scoreMove(before, after) counts resolveMove's result for the mover: +config.scoreKill per enemy destroyed, config.scoreWall when the mover dies at the wall, both for hit-then-wall, negative scores allowed (human decisions 2026-11-09); tests in tests/score.test.js; game.js computes it at launch and applies it when the move ends (section 6).
- How a user reaches it: automatically after every move
- How an agent drives it: unit tests calling rules.resolveMove(state, move); verify.sh --feature hits
- Inputs: ship A at (200, 480), enemy B at (300, 490), A moves 150 at 0°
- Correct output looks like: B is destroyed; A survives at (350, 480). Hit-then-wall destroys both. Grazing contact counts as a hit. An enemy that has not moved since it spawned and still sits on its spawn point survives (spawn protection, T-006); a protected mover that reaches the wall still dies. Score: A gets +1 for destroying B; a wall death gives the mover -2; hit-then-wall gives -1; sweeping a protected enemy scores nothing (T-012).
- Known traps: checking only the end position instead of the swept area; missing grazing contacts; tunneling through the enemy on long moves; checking the wall before the enemy
- Owner role: Reviewer owns the test cases; Owner owns the code

6. Respawn & Turns
- What it does: "When a ship is destroyed, a new one appears at its spawn point and play continues."
- Where it lives: src/rules.js endTurn(state) (pure: every ship with alive: false is replaced by config.spawns[i], read at call time, with alive: true and unmovedSinceSpawn: true; living ships unchanged; turn flips exactly once, also after a double kill; other fields kept); src/game.js step(ms) (turn manager: when the move animation ends it puts the resolved end state in place and calls endTurn once, so the next player starts on the power gauge; nothing else changes the turn, so there is no turn timer); tests in tests/turns.test.js and tests/game.test.js (T-005). A destroyed enemy stays drawn until the move ends and reappears at its spawn in the same step. In that same step, before endTurn, input.startExplosions adds one entry per destroyed ship to state.explosions (a hit enemy where it was hit; the wall-killed mover moved the shortest distance that puts its whole triangle inside the map), and input.stepExplosions ages them on every step and removes them at config.explosionMs. Explosions are decoration: play does not wait for them and they never change turn, ships or gauge (T-007, human answer 2026-11-09). Score (T-012): in that same step, before endTurn, game.js puts in the scores that rules.scoreMove computed when the move was launched (kept in anim.scores), so a score never changes before the player sees the hit; endTurn keeps scores unchanged.
- How a user reaches it: automatically after a destruction or the end of a move
- How an agent drives it: __game.setState() with a destroyed ship, then getState(); verify.sh --feature turns
- Inputs: Player 1 destroys Player 2's ship
- Correct output looks like: Player 2's ship reappears at its spawn point, it becomes Player 2's turn, the game never ends, and there is no turn timer
- Known traps: skipping a turn after a double kill; making spawn points attackable. Spawn protection is settled (human decision 2026-11-09, A2, T-006): a ship that has not moved since it spawned (createInitialState or endTurn respawn) and still sits on its spawn point cannot be destroyed by an enemy sweep; any accepted move of its own ends it, including a distance-0 launch (human decision 2026-11-09). No time limit and no other protection. Traps: a protection flag alone would survive a setState teleport (scripts/smoke.mjs turnsProbe copies ship 1 from getState()), so isSpawnProtected also checks the position; ships without the field (scenario states) are not protected. Shown on screen (T-010): a protected ship's outline blinks (fades out over config.protectionBlinkMs, snaps back, repeats; section 2), so both ships blink at game start and a respawned ship blinks until its own next move.
- Owner role: Owner

7. Config
- What it does: "I can tune the game numbers in one place."
- Where it lives: src/config.js
- How a user reaches it: edit the file and reload
- How an agent drives it: grep for hard-coded numbers outside config.js; verify.sh --feature config
- Inputs: change max move from 150 to 200
- Correct output looks like: gauges, movement, and tests all use 200 with no other edits
- Known traps: magic numbers scattered across files; tests hard-coding values instead of reading config
- Owner role: Reviewer

8. Paved roads (one way to do each common job)
- New game rule: add a pure function to src/rules.js and its test file in tests/ using the rules.test.js pattern. No DOM or canvas code in rules.
- New drawn element: add a draw<Thing>(ctx, state) function in src/render.js. Read from state only, never change it.
- New control: add it in src/input.js and expose it through __game.press().
- Data access: no database or API in Prototype 1. All game state lives in one state object owned by src/game.js.
- Errors and logging: use src/log.js (log.info, log.warn, log.error), silent unless ?debug=1. No bare console.log.
- Tests: tests/<feature>.test.js with Node's built-in test runner (node --test). Copy the pattern from tests/rules.test.js.

9. Test harness contract (set 2026-11-07; changing it needs a brief)
- Files: scripts/run-scenario.mjs (rules scenarios), scripts/smoke.mjs (headless Chrome/Edge, no npm dependencies; set CHROME_PATH to choose a browser), scripts/serve.mjs (static server; npm run dev serves http://localhost:5173/index.html), scenarios/*.json (inputs), expected/*.json (correct output).
- No-comments guard (T-023): scripts/no-comments.mjs (findComments(text, kind) with kind js | sh | html; checkTree(root); run directly it prints GUARD FAIL [no-comments] plus one path:line: text per finding and exits 1, silent and exit 0 when clean) and tests/no-comments.test.js fail when a code file holds a comment. Files covered, found by walking the disk (untracked files too, node_modules skipped): .js and .mjs in src/, tests/ and sim/ at any depth; .js, .mjs and .sh in scripts/; index.html (HTML comments, block comments in <style>, inline <script> bodies); .js, .mjs, .sh and .html in agent-team/evidence/. Allowed exceptions: a shebang on line 1; the two scanner directives, each only in its own file with its exact text (scripts/run-scenario.mjs: nosemgrep javascript.lang.security.insecure-object-assign.insecure-object-assign; scripts/smoke.mjs: nosemgrep javascript.lang.security.detect-insecure-websocket.detect-insecure-websocket); evidence folders whose name starts with T-001 to T-014. Not checked: .github/, .gitattributes, .claude/, docs/, JSON, Markdown. Enforced through the unit tests of every verify.sh run (any --feature) and so in CI on pull requests; a bare ./scripts/guards.sh run does not check it. A new scanner directive, or a here-document in a .sh file, needs a brief that changes the checker.
- Stale-handoff check (T-016): scripts/handoff-check.mjs (taskFromBranch(name); checkHandoff(root, task) returns { result: PASS | FAIL | SKIP, reason, commit, subject }; report(outcome) gives the printed lines and the exit code; run directly as `node scripts/handoff-check.mjs [TASK]` it prints `PASS handoff names the latest code commit`, or `FAIL handoff names the latest code commit` plus `Handoff does not name <C>; latest code commit is <C> (<subject>)` and exits 1, or `SKIP handoff check (<reason>)`) and tests/handoff-check.test.js fail the unit tests, and so every verify.sh run, when the Handoff section of the task's brief does not name the latest code commit C. Task ID: from the current branch name task/T-###-short-name (three or more digits), or from the argument when run by hand (T-### or T-###-review); verify.sh does not pass it. C: walking back from HEAD along first parents, the first commit whose diff against its first parent (the root commit: against nothing) touches a path outside agent-team/; a merge that brings in code counts. PASS when the Handoff section (from "## Handoff" to the next "## " heading) of agent-team/tasks/T-###.md, read from the working tree, contains the first 7 characters of C. Skipped, never a failure: no task branch (master, another branch name, a detached HEAD as in CI), no brief for the task, a Handoff that is still the "(owner fills in)" placeholder, a brief whose top Status line is DONE, a folder that is not the top of a git repo, git missing. Working rule: after a new code commit on a task whose Handoff is filled in, first update the Handoff to name the new commit (saving the file is enough), then run verify.sh; a task that changes nothing outside agent-team/ names the commit the FAIL message gives. git is called only through execFileSync('git', [arguments]) with read-only commands; the tests build their fixture repos in the OS temp dir and remove them.
- scenarios/ and expected/ are the spec. The owner never edits them to make a check pass; a wrong expectation goes back to the coordinator as a new brief.
- Smoke checks save a screenshot next to their output in agent-team/evidence/T-###/ for the reviewer.
  - input also saves one screenshot per gauge phase (T-008): input-smoke-power.png (phase 'power'), input-smoke-direction.png (phase 'direction', backward false) and input-smoke-direction-backward.png (phase 'direction', backward true, after Shift). Each is taken in its own page, separate from the pages behind the checked results; smoke.mjs reads getState().gauge just before and after each capture and fails the run with an error naming the file if the phase or backward flag is wrong. input-smoke.png (after the launch) is still written.
  - turns also saves three checked screenshots (T-017): turns-smoke-backward-mid.png (a backward launch with needle 30 half-way through its flight: phase 'moving', mover strictly between start and end, heading = wrapped heading before launch + 180 + needle within 1e-6), turns-smoke-backward-end.png (same launch after the move: phase 'power', turn passed, mover on the rules.applyMove end point within 0.001, heading kept) and turns-smoke-explosion.png (a kill, then half of config.explosionMs after the move ends: an explosions entry for the destroyed ship with 0 < elapsed < config.explosionMs, that ship respawned at its spawn). Each is taken by stateShot in its own page opened after the checked turns page; the page's animation loop is stopped first (freezeLoopProbe replaces the page's requestAnimationFrame and keeps the loop callback as window.__redraw, which draws with step(0)), state.clock is set to 0 and time moves only through __game.step(ms), so the pictures are the same on every run; the state is read just before (after a redraw) and just after each capture, and a wrong state fails the run with an error naming the file, so the diff against expected/turns-smoke.json fails without any new result key. turns-smoke.png is still written.
- Every slice must keep guards green, so src/rules.js has to exist from slice 1 (it may start with just the functions below as they are built).
- Config: src/config.js has a default export of one plain, mutable object with at least worldWidth, worldHeight, shipSize, maxMove and spawns: [{x, y, heading}, {x, y, heading}]. Rules read it at call time, so a scenario can override values.
- State: { turn: 0 | 1, ships: [{x, y, heading, alive, unmovedSinceSpawn?}, {x, y, heading, alive, unmovedSinceSpawn?}], gauge, scores? }. unmovedSinceSpawn (T-006) is true from createInitialState or an endTurn respawn until the ship's own accepted move sets it to false; a ship without it is treated as false. scores (T-012): [p1, p2], set by createInitialState from config.scoreStart; a state without scores (scenario states, older test states) counts as both on config.scoreStart (rules.currentScores), so scenarios and expected/ are unaffected. Optional explosions: [{ ship, x, y, heading, elapsed }] (ship index, centre, heading, ms since it began; T-007), absent or [] when nothing is exploding; move animation in anim (section 4). Optional clock (T-010): game time in ms, 0 when game.js starts and grown by exactly ms on every step(ms) (a state without it counts from 0); only render.js reads it (protection blink); rules ignore it. Game units; heading in degrees, 0 = right (+x), 90 = down (+y), kept within 0 to 360.
- Move: { distance, angle, backward? }. angle is the world travel direction in degrees (same convention as heading).
- Rules (pure, return a new state, never mutate input; run-scenario.mjs freezes inputs to enforce this):
  - createInitialState(): builds { turn: 0, ships at config.spawns[i] with alive: true and unmovedSinceSpawn: true, gauge, scores: [scoreStart, scoreStart] } from config at call time (T-001). game.js uses it to start the game.
  - applyMove(state, move): moves ships[state.turn]; every accepted move, forward or backward, sets heading to wrapDegrees(angle) (T-009); sets the mover's unmovedSinceSpawn to false for any accepted move (distance 0 included); a move over maxMove returns the state unchanged.
  - resolveMove(state, move): applyMove plus swept-area hits and walls; destroyed ships get alive: false, except a spawn-protected enemy, which stays alive. No respawn, no turn change.
  - isSpawnProtected(state, i): true only if ships[i] is alive, has unmovedSinceSpawn === true and sits on config.spawns[i] (read at call time, within 1e-9). Used by resolveMove; T-010 draws it.
  - endTurn(state): respawns destroyed ships at config.spawns[i] with unmovedSinceSpawn: true (living ships unchanged) and passes the turn; scores are kept. game.js calls it after the move animation.
  - scoreMove(before, after) (T-012): new scores array for the move from before to after = resolveMove(before, move). Only the mover (before.turn) scores: config.scoreKill (1) per enemy that went from alive to destroyed, config.scoreWall (-2) if the mover was destroyed (the wall); hit-then-wall gets both (net -1); no clamping at 0. currentScores(state) returns state.scores or [scoreStart, scoreStart].
- Gauge (in getState().gauge): { phase: 'power' | 'direction' | 'moving', power: 0..1, needle: degrees relative to the ship's heading (0 = straight ahead), backward: boolean, distance }. distance = power × maxMove once locked.
- Debug API: getState() returns a copy; setState(state) accepts a modified copy; press() and real keydown events both work and keydown with repeat is ignored; step(ms) finishes the move animation and calls endTurn.
