Feature Map - product-a (Galaxy Shooter - Prototype 1)
Feature plan doc: docs/PLAN.md source of truth for game features plan.
Roles: Coordinator, Owner, Reviewer.

1. Agent test hook (applies to all features)
The game draws on a canvas, so agents can't click elements. src/game.js exposes a debug API when the URL has ?debug=1:
- window.__game.getState(): ships, positions, headings, turn, gauge state
- window.__game.press('Space' | 'Shift'): simulates input
- window.__game.setState(state): loads a test scenario
- window.__game.step(ms): advances the game clock
Command-line checks: ./scripts/verify.sh T-### --feature <name> (<name>: render, input, movement, hits, turns, config, balance or all) always runs guards, lint and all unit tests (node --test tests/*.test.js), then that feature's scenario and/or browser smoke check. Every verify.sh log starts with a commit line and a `dirty:` line, and the guards include the format-string guard (both T-036, section 9). --feature all (the default) runs every feature, so it only passes once the whole prototype is built. See section 9 for the harness contract.

2. Map & Rendering
- What it does: "I see the play area full screen with two triangle ships."
- Where it lives: src/render.js, src/config.js (ship triangle: rules.shipPoints, re-exported by render.js, T-004). Explosions (T-007): render.js explosionPieces(explosion, elapsedMs) (pure: the ship's outline triangle, each side cut once at config.explosionCuts, 6 pieces whose midpoints move straight out from the centre at config.explosionSpeed units/s and that shrink about their midpoints from 1 to config.explosionEndScale over config.explosionMs) and drawExplosions(ctx, state) (outline pieces in COLORS.ships[ship], config.shipLineWidth; drawFrame calls it before drawShips). Scores (T-012): drawScores(ctx, state) draws player 1's score top-left and player 2's top-right (right-aligned), each in its ship colour, config.scoreFontSize, config.scoreMargin inside the map; drawFrame calls it right after drawMap. Spawn protection blink (T-010): render.js protectionAlpha(clockMs) (pure: each cycle of config.protectionBlinkMs (600) falls linearly from 1 to config.protectionMinAlpha (0), then snaps back to 1; no fade back in; read at call time); drawShips strokes a ship with globalAlpha protectionAlpha(state.clock) when rules.isSpawnProtected(state, i) is true, else 1, and resets globalAlpha to 1 after every ship, so gauges and the other ship are unchanged. state.clock is advanced only by game.js step(ms) (section 9). Title decal (T-011): render.js drawTitle(ctx) (reads nothing from state) strokes config.titleText ("Delta Fray", the human's words) upper-cased as "DELTA FRAY", outline only in COLORS.dim, monospace config.titleFontSize, config.titleLetterSpacing, config.titleLineWidth, textAlign centre at x = config.worldWidth / 2, config.titleTop below the top edge; wrapped in ctx.save/restore so later draws keep their own settings; drawFrame calls it last, after every other draw call. Decoration only: not in state or rules.js, so movement, hits and walls are unchanged
- How a user reaches it: open index.html through a local server (e.g., npx serve .)
- How an agent drives it: ?debug=1, then __game.getState(); screenshot the canvas; verify.sh --feature render
- Inputs: world 1280 × 960 units, browser window 1920 × 1080
- Correct output looks like: world scaled to fit with aspect ratio kept; ships are 30-unit triangles at their spawn points, pointing at each other; no scrollbars; a destroyed ship's outline breaks into 6 uneven pieces that fly outward and shrink to half size over 1 second while play carries on (T-007); a spawn-protected ship's outline fades out over 600 ms, snaps back and repeats until that ship moves (T-010); "DELTA FRAY" in outline capitals at the top centre, over everything, ships visible through and under it (T-011)
- Known traps: mixing screen pixels with game units; stretching the map at other aspect ratios; blurry canvas on high-DPI screens
- Code notes (T-024): the three config.explosionCuts entries are, in order, the cut on the tip-left, left-right and right-tip side, where tip, left and right are shipPoints entries 0, 1 and 2 (the names drawShips gives them; at heading 0 "left" is the corner with the larger y, lower on screen). COLORS.dim (map border, power bar outside the power phase, dial arc, title) has about 8:1 contrast against COLORS.background (8.13:1, WCAG 2). fitCanvas(canvas, viewWidth, viewHeight, dpr) sets the CSS size from fitScale and the backing store to that size times dpr (game.js passes window.devicePixelRatio, or 1), which is what keeps the canvas sharp on a 2x screen. drawShips sets lineJoin 'round' so the stroke stays within lineWidth / 2 of each corner (a miter at the narrow tip would reach further; tests/config.test.js checks the spawned ships with that lineWidth / 2 margin).
- Owner role: Owner

3. Controls & Gauges
- What it does: "I press Space to set distance, Shift to flip backward, Space again to launch."
- Where it lives: src/input.js (pure: stepGauge(state, ms), pressKey(state, 'Space' | 'Shift'), keyFromEvent(event)); keydown listener, animation loop and debug API in src/game.js; drawGauge / drawPowerBar / drawDirectionDial / gaugeLayout(state) in src/render.js (drawn only on the ship whose turn it is and following its position and heading every frame: power bar at 0.3 of base size a fixed distance below the ship that clears the dial in every heading, so it never moves with the phase; fixed-size direction dial at 0.56 of base size just in front of the nose, or just behind the tail when backward, on the long axis; clamped inside the map near edges); sweep speeds, needle range and gauge layout in src/config.js (gauge*) (T-002)
- Gauge state notes (T-002): the gauge also carries sweep: 1 | -1 (direction the active reading moves in), so a gauge edited through setState keeps sweeping smoothly. Both readings bounce back and forth. needle stays within -gaugeNeedleMax..+gaugeNeedleMax, positive = clockwise; backward: false measures it from the nose (world angle = heading + needle), backward: true from the tail (world angle = heading + 180 + needle). Shift toggles backward in the direction phase only. In the moving phase step(ms) runs the move animation instead (section 4); a moving phase with no anim (only reachable through the debug setState) is reset to the power phase on the next step(ms) > 0, ship unmoved, turn unchanged (T-014, human decision 2026-11-09).
- How a user reaches it: keyboard during their turn
- How an agent drives it: __game.press('Space'), __game.step(ms), __game.press('Shift'), __game.press('Space'), then check getState().gauge; verify.sh --feature input
- Inputs: Space at a 60% power reading; no Shift; Space at a 30° needle reading
- Correct output looks like: distance locked at 90 units (60% of 150), direction 30° forward, launch starts immediately with no confirm step
- Known traps: key-repeat registering multiple presses; Shift working after the direction is locked; gauges sweeping too fast for careful aim; adding a path preview (not allowed)
- Code notes (T-024): config.gaugePowerSweepMs is the time for one pass of the power reading from 0 to 1, not for there and back; config.gaugeNeedleSweepMs is the time for one pass across the whole needle range (-gaugeNeedleMax to +gaugeNeedleMax). input.js bounce(value, dir, delta, min, max) moves the value by delta along a triangle wave between min and max and returns { value, dir }, the new value and the direction (1 or -1) it is now moving in; stepGauge uses it for both readings. gaugeLayout measures the dial reach from the nose because the nose is the ship point farthest from its centre (true whenever shipWidth < shipSize, which tests/config.test.js requires); the power bar is offset from the ship by that reach plus config.gaugePowerGap, below the ship or, near the bottom edge, above it (tests/render.test.js checks that bar and dial do not overlap at mid-map, every 15 degrees, forward and backward). tests/render.test.js compares config.gaugePowerScale with 0.5 x 0.6 (0.3) and config.gaugeDialScale with 0.7 x 0.8 (0.56) as numbers pinned on purpose instead of reading config, because they are the human's decisions of 2026-11-08 (DECISIONS.md); they change only with a new human decision.
- Owner role: Owner

4. Movement
- What it does: "My ship flies the distance and direction I chose."
- Where it lives: src/rules.js applyMove(state, move) and wrapDegrees (math; a move longer than config.maxMove is refused and the state returned unchanged, human decision 2026-11-08; every accepted move, forward or backward, sets the heading to the wrapped travel angle, so a backward move turns the ship to face its path at launch, flies tip first and keeps that heading, human decisions 2026-11-09, T-009); src/input.js moveFromGauge(state) (locked gauge to Move), pointAlong(from, to, t), startMove(state, end) and stepMove(state, ms) (animation progress kept in state.anim = { from, to, ships, elapsed, scores? } (scores added by game.js at launch, T-012), where ships is every ship of the rules.resolveMove end state; only the mover goes along the straight segment at constant speed, and at the end all of anim.ships is put in place, so the mover ends exactly on the rules result and a destroyed enemy stays destroyed; the gauge returns to the power phase; a moving phase with no anim, only reachable through the debug setState, is reset by stepMove to the power phase on the next step(ms) > 0 with every ship unmoved, no move built and the turn unchanged, so game.js calls no endTurn: T-014, human decision 2026-11-09); src/game.js press() launches on the second Space with rules.resolveMove, and step(ms) runs stepMove and, in the step where the animation ends, calls rules.endTurn once (section 6) (T-003, T-005); drawShips in src/render.js draws the ship where state puts it (no path, trail or end marker); animation length config.moveAnimMs (T-003)
- How a user reaches it: the second Space press
- How an agent drives it: unit test calling rules.applyMove(state, {distance, angle}) (tests in tests/movement.test.js); tests/game.test.js loads src/game.js in Node with a stubbed DOM and drives __game.press/step; verify.sh --feature movement
- Inputs: ship at (200, 480) heading 0°, move 150 units at 0°
- Correct output looks like: ship ends at (350, 480). Every move, forward or backward, turns the heading to the travel direction and keeps it: a backward move (Shift) snaps the ship to face its path at launch, flies tip first, and on its next turn the gauges sit at the new nose (T-009).
- Known traps: degrees vs. radians; y-axis pointing down on canvas; allowing distance over 150; letting the animation, not rules.js, decide the final position
- Code notes (T-024): input.pointAlong(from, to, t) clamps t to 0..1, which is why the move animation never overshoots its end point.
- Owner role: Owner

5. Hit Detection & Edges
- What it does: "If my path sweeps over the enemy, it explodes. If I reach the wall, I explode."
- Where it lives: src/rules.js resolveMove(state, move) (applyMove, then the convex hull of the mover's start and end triangles in its new heading (the travel angle, for backward moves too, T-009), as input.startMove turns the ship before it moves; separating axis test against each living enemy, touching counts, except an enemy for which isSpawnProtected(state, j) is true, which survives the sweep (human decision 2026-11-09, A2; T-006); the mover is destroyed if any hull corner touches or crosses 0..config.worldWidth or 0..config.worldHeight, human decision 2026-11-09; a move over maxMove returns the state unchanged) and shipPoints(ship, size, width) (the one ship triangle, also drawn by render.js); tests in tests/hits.test.js (T-004) and tests/spawn.test.js (T-006). Called by src/game.js press() for every launched move (T-005). Score (T-012): src/rules.js scoreMove(before, after) counts resolveMove's result for the mover: +config.scoreKill per enemy destroyed, config.scoreWall when the mover dies at the wall, both for hit-then-wall, negative scores allowed (human decisions 2026-11-09); tests in tests/score.test.js; game.js computes it at launch and applies it when the move ends (section 6).
- How a user reaches it: automatically after every move
- How an agent drives it: unit tests calling rules.resolveMove(state, move); verify.sh --feature hits
- Inputs: ship A at (200, 480), enemy B at (300, 490), A moves 150 at 0°
- Correct output looks like: B is destroyed; A survives at (350, 480). Hit-then-wall destroys both. Grazing contact counts as a hit. An enemy that has not moved since it spawned and still sits on its spawn point survives (spawn protection, T-006); a protected mover that reaches the wall still dies. Score: A gets +1 for destroying B; a wall death gives the mover -2; hit-then-wall gives -1; sweeping a protected enemy scores nothing (T-012).
- Known traps: checking only the end position instead of the swept area; missing grazing contacts; tunneling through the enemy on long moves; checking the wall before the enemy
- Code notes (T-024): the internal convexHull in src/rules.js uses the monotone chain method (points sorted by x, then y); the hull comes out counter-clockwise by the cross product of screen x and y (it looks clockwise on screen, where y points down), and collinear points are dropped. No caller depends on the winding: polygonsOverlap tests the edge normals of both polygons and the wall test reads only the corners.
- Owner role: Reviewer owns the test cases; Owner owns the code

6. Respawn & Turns
- What it does: "When a ship is destroyed, a new one appears at its spawn point and play continues."
- Where it lives: src/rules.js endTurn(state) (pure: every ship with alive: false is replaced by config.spawns[i], read at call time, with alive: true and unmovedSinceSpawn: true; living ships unchanged; turn flips exactly once, also after a double kill; other fields kept); src/game.js step(ms) (turn manager: when the move animation ends it puts the resolved end state in place and calls endTurn once, so the next player starts on the power gauge; nothing else changes the turn, so there is no turn timer); tests in tests/turns.test.js and tests/game.test.js (T-005). A destroyed enemy stays drawn until the move ends and reappears at its spawn in the same step. In that same step, before endTurn, input.startExplosions adds one entry per destroyed ship to state.explosions (a hit enemy where it was hit; the wall-killed mover moved the shortest distance that puts its whole triangle inside the map), and input.stepExplosions ages them on every step and removes them at config.explosionMs. Explosions are decoration: play does not wait for them and they never change turn, ships or gauge (T-007, human answer 2026-11-09). Score (T-012): in that same step, before endTurn, game.js puts in the scores that rules.scoreMove computed when the move was launched (kept in anim.scores), so a score never changes before the player sees the hit; endTurn keeps scores unchanged.
- How a user reaches it: automatically after a destruction or the end of a move
- How an agent drives it: __game.setState() with a destroyed ship, then getState(); verify.sh --feature turns
- Inputs: Player 1 destroys Player 2's ship
- Correct output looks like: Player 2's ship reappears at its spawn point, it becomes Player 2's turn, the game never ends, and there is no turn timer
- Known traps: skipping a turn after a double kill; making spawn points attackable. Spawn protection is settled (human decision 2026-11-09, A2, T-006): a ship that has not moved since it spawned (createInitialState or endTurn respawn) and still sits on its spawn point cannot be destroyed by an enemy sweep; any accepted move of its own ends it, including a distance-0 launch (human decision 2026-11-09). No time limit and no other protection. Traps: a protection flag alone would survive a setState teleport (scripts/smoke.mjs turnsProbe copies ship 1 from getState()), so isSpawnProtected also checks the position; ships without the field (scenario states) are not protected. Shown on screen (T-010): a protected ship's outline blinks (fades out over config.protectionBlinkMs, snaps back, repeats; section 2), so both ships blink at game start and a respawned ship blinks until its own next move.
- Owner role: Owner

8. Paved roads (one way to do each common job)
- New game rule: add a pure function to src/rules.js and its test file in tests/ using the rules.test.js pattern. No DOM or canvas code in rules.
- New drawn element: add a draw<Thing>(ctx, state) function in src/render.js. Read from state only, never change it.
- New control: add it in src/input.js and expose it through __game.press().
- Data access: no database or API in Prototype 1. All game state lives in one state object owned by src/game.js.
- Errors and logging: use src/log.js (log.info, log.warn, log.error), silent unless ?debug=1. No bare console.log.
- Tests: tests/<feature>.test.js with Node's built-in test runner (node --test). Copy the pattern from tests/rules.test.js. tests/game.test.js records console.info while it imports src/game.js, and one test pins the single start-up log line ('[game]', 'game started', the state), so a changed start-up message or a second log.info at module load fails that test on purpose; change the test with it.

9. Test harness contract (set 2026-11-07; changing it needs a brief)
- Files: scripts/run-scenario.mjs (rules scenarios), scripts/smoke.mjs (headless Chrome/Edge, no npm dependencies; set CHROME_PATH to choose a browser), scripts/serve.mjs (static server; npm run dev serves http://localhost:5173/index.html), scenarios/*.json (inputs), expected/*.json (correct output).
- run-scenario.mjs (T-024): usage `node scripts/run-scenario.mjs scenarios/<name>.json --out <file.json>` (a missing argument prints that line and exits 2). Scenario file format: `{ "overrides": {config keys}, "cases": [ { "name", "state", "steps": [{ "call", "move"? }], "pick": ["ships.0.x", ...] } ] }`, and a case may carry its own "overrides". Each step calls rules[call](state, move), or rules[call](state) when the step has no move, and must return the new state. The output holds, per case name, each "pick" path with its value, numbers rounded to 3 decimals (-0 written as 0, a missing path as "<missing>"), or { "error" } for a case that could not run; exit code 1 if anything could not run. Before every case config is reset to its values at start (keys added by an earlier case removed), then takes the scenario's and then the case's overrides. Overrides come from scenario files in the repo (verify.sh passes scenarios/<name>.json), never from user input, which is why the nosemgrep directive on that Object.assign line is safe.
- serve.mjs (T-024, T-042): set PORT to change the port of npm run dev (default 5173); it listens on 127.0.0.1 (smoke.mjs starts it on the project root on a free port during every browser verify run). Since T-042 it serves only what the game loads and answers each request in this order: (1) the Host header, lower-cased, must be `127.0.0.1:<port>` or `localhost:<port>` with the port it really listens on, otherwise 421 `Misdirected request`, a missing or empty Host included (createServer runs with requireHostHeader: false, so Node's own 400 does not answer first); this is what stops a page from reading files through DNS rebinding; (2) a raw (undecoded) URL path that holds %2F or %5C in either case gets 404; (3) the URL pathname is decoded with decodeURIComponent (400 `Bad request` on a bad escape), and only `/` alone maps to /index.html (any other path that ends in `/` gets 404); (4) a decoded path that holds a backslash, a colon, a `~` or a control character (U+0000 to U+001F, U+007F) gets 404 on every platform (a raw, unencoded backslash in the request target never reaches this step: the URL parser has already turned it into `/`, so `/src\game.js` is answered as /src/game.js; harmless, because only allowed files are reachable that way, T-042 security review round 1, Issue 2); (5) allow-list, exact case: the path must be `/index.html` or match `^/src/(?:[A-Za-z0-9_-]+/)*[A-Za-z0-9_-]+\.js$`, everything else gets 404; (6) every path part, lower-cased, must not start with `.`, equal `secrets`, or end with `.` or a space; (7) the file is resolved with fs.promises.realpath, the native realpath (the root's real path is taken the same way once, before it listens, and startServer rejects when the root cannot be resolved), never the JavaScript fs.realpathSync or the callback fs.realpath, which on Windows keep an 8.3 name such as ENV~1 and the requested case (T-024 security review round 2); the real path must lie inside the real root (path.relative with no `..` first part and not absolute), its parts split on `/` and `\` must pass (6), and written with `/` it must pass (5) and equal the requested path exactly (owner choice, stricter than the brief: a case alias such as /src/Game.js or a link inside src/ to another allowed file gets 404 too); a realpath error gets 404; (8) the file is read and sent with 200, its TYPES Content-Type and Cache-Control: no-store (404 `Not found` on a read error). A new file type for the game (CSS, images, JSON) is refused by the allow-list and needs a brief that widens it. tests/serve.test.js (12 tests) builds a throw-away root of fake files and links in the OS temp dir for each test and sends real requests for every bypass kind found in T-024 and T-042: encoded separators, case variants, 8.3 short names (with a diagnostic on Windows saying whether they existed), NTFS stream names, trailing dots and spaces, folder links to secrets/ and outside the root, a file symlink src/env.js to .env (skipped with its reason where the OS user may not make one), wrong and missing Host headers, dotfiles, other files, control characters, device names and a bad escape; plus every allowed request, a server started on a folder link to the root, and a root that cannot be resolved; it fails 10 of its 12 tests against the old serve.mjs (agent-team/evidence/T-042/negative-control.txt). Run on Windows only (Node v24.15.0, 8.3 names present in the fixtures; agent-team/evidence/T-042/probe-after.txt: every probe request outside the allowed ones got 404, 400 or 421 and none returned a fake body); Linux and macOS not run. Known limits: a hard link under src/ to another file resolves to its own src/ path and would be served (making one needs write access to src/); a file swapped between the realpath call and the read is not caught (needs write access to the root); methods other than GET are answered as today; on a case-insensitive macOS volume, whether realpath gives the on-disk case, and so whether /src/Game.js gets 404, is not known (it could only serve the allowed game.js). scripts/serve.mjs and tests/serve.test.js are protected from agent edits (deny list in .claude/settings.json and the CI step "Block changes to the checks"; added by the human after the T-042 merge in 3ad3ebf), so a change to either, a wider allow-list included, goes by route A.
- smoke.mjs (T-024): usage `node scripts/smoke.mjs --feature render|input|turns --out <file.json>`; the output is named true/false checks ({ "error" } when the run fails), which verify.sh compares with expected/<feature>-smoke.json. It talks to the browser over the DevTools protocol with Node's built-in WebSocket (no npm dependency). Without CHROME_PATH it tries Chrome, then Edge, in the Windows program folders, then Chrome or Chromium at the macOS and Linux paths. Besides the "DevTools listening on" line on stderr it reads the DevToolsActivePort file in the profile, because a browser started from a shell without a console hands off to a detached browser and prints no address (commit ef1704e). The local DevTools address on 127.0.0.1 only speaks plain ws and nothing leaves the machine, which is why the nosemgrep directive on that line is safe. At the end it closes the browser with Browser.close (the launcher process may be gone while the browser runs on) and waits for the profile lockfile to go before deleting the profile. The probe functions are sent to the page as source text inside the Runtime.evaluate expression and run inside the browser, not in Node, so they can use only page globals and their arguments.
- Balance sim (T-024): sim/balance.mjs plays scripted games with the real rules (src/config.js, src/rules.js, input.moveFromGauge), 300 moves each, and exits 1 if a target in agent-team/design/balance-targets.json is missed; usage `node sim/balance.mjs --games 2000 --out <file.json>`, run from the repo root (it reads the targets file by a relative path). scripts/verify.sh runs it as the `balance` feature, which is part of `--feature all`. The scripted player aims roughly at the enemy within what the gauge allows (needle within gaugeNeedleMax of the nose, or of the tail when the enemy is more than 90° off the nose) and builds its move with input.moveFromGauge, the same move the real controls produce. The metric names (movesToFirstEncounter, edgeDeathRate) must match balance-targets.json; a target with no metric fails. movesToFirstEncounter counts moves per player: turns alternate, so the number of the move with the first hit is halved and rounded up. The random numbers are seeded (seed = game number), so the same code always gives the same result.
- Test-case notes (T-024): the reasoning behind individual test cases in tests/hits.test.js, tests/spawn.test.js, tests/game.test.js, tests/render.test.js and tests/config.test.js is recorded in agent-team/evidence/T-022/inventory.md and, word for word, in agent-team/evidence/T-022/before-comment-list.txt; it is not copied here.
- No-comments guard (T-023): scripts/no-comments.mjs (findComments(text, kind) with kind js | sh | html; checkTree(root); run directly it prints GUARD FAIL [no-comments] plus one path:line: text per finding and exits 1, silent and exit 0 when clean) and tests/no-comments.test.js fail when a code file holds a comment. Files covered, found by walking the disk (untracked files too, node_modules skipped): .js and .mjs in src/, tests/ and sim/ at any depth; .js, .mjs and .sh in scripts/; index.html (HTML comments, block comments in <style>, inline <script> bodies); .js, .mjs, .sh and .html in agent-team/evidence/. Allowed exceptions: a shebang on line 1; the two scanner directives, each only in its own file with its exact text (scripts/run-scenario.mjs: nosemgrep javascript.lang.security.insecure-object-assign.insecure-object-assign; scripts/smoke.mjs: nosemgrep javascript.lang.security.detect-insecure-websocket.detect-insecure-websocket); evidence folders whose name starts with T-001 to T-014. Not checked: .github/, .gitattributes, .claude/, docs/, JSON, Markdown. Enforced through the unit tests of every verify.sh run (any --feature) and so in CI on pull requests; scripts/guards.sh line 39 runs `node scripts/no-comments.mjs || FAIL=1` (since 4e83e53), so a bare ./scripts/guards.sh run checks it too. A new scanner directive, or a here-document in a .sh file, needs a brief that changes the checker.
- Conflict-marker guard (T-018): scripts/conflict-markers.mjs (findMarkers(text) returns [{ line, text }]; checkTree(root) returns [{ file, line, text }] with paths relative to root, forward slashes, files in sorted order; report(found) returns { lines, code }: { lines: [], code: 0 } for an empty list, otherwise lines is the GUARD FAIL message followed by one path:line: text per finding in the given order, and code 1; run directly it prints GUARD FAIL [no-conflict-markers]: Resolve the merge conflict; never commit conflict markers, then one path:line: text per finding, and exits 1, silent and exit 0 when clean) and tests/conflict-markers.test.js fail when any file in the repo holds a git conflict marker line. Marker rule: a line that starts in column 1 with exactly seven `<`, seven `>` or seven `|` characters, followed by a space or the end of the line (a carriage return right before the line feed counts as the end of the line). Not a marker: anything before it on the line (so a saved diff or a `path:line: text` log line is safe), eight or more of the character, seven followed by a letter or a tab, and a bare line of seven `=` (not checked on its own; it appears in Markdown and text). Files checked: every file under the repo root at any depth, found by walking the disk with no git call, so untracked files and every file type are checked (Markdown, logs and evidence included). Not opened: anything named .git (folder or file), any folder named node_modules or secrets, any file named .env or starting with `.env.`, symbolic links and junctions (not followed), and binary files (a zero byte in the first 8000 bytes, the rule git uses).
